## 1. Why it exists

`imagegen` had two backends and both take exactly one image. Every request that means "put the
person from this picture into that one" or "change only the hair" was unbuildable, in the node and
in the chat alike.

Qwen-Image-2.1 answers both with one model: `QwenImage21Pipeline.__call__` accepts a prompt plus up
to ten condition images, and its documented local-editing mechanism is the original image and a
separate mask as two of them. That is why this is a third backend rather than a replacement - it is
the only one that can serve `/edit` and `/mask`, and it is also the only one whose weights are
non-commercial.

---

## 2. The decision that shapes everything: a mask is an image

**`QwenImage21Pipeline.__call__` has no `mask_image` parameter.** Its full signature is
`prompt, image, negative_prompt, true_cfg_scale, height, width, num_inference_steps, sigmas,
num_images_per_prompt, generator, latents, prompt_embeds, ..., output_resolution, use_kv_cache`.
The `image` argument takes a PIL image or a **flat list** of them, and that list is the only channel
into the model.

Masking is nevertheless a first-class, trained capability. The model card names three ways to mark a
region - coloured circles, painted annotations, and "the original image and a separate mask as two
inputs" - and all three are the same mechanism: **an extra condition image**.

So `/edit` appends the mask to the condition list and adds a sentence to the prompt saying the last
image is a mask. Two consequences follow, and both are load-bearing:

* **Anyone looking for where `mask_image` went should stop looking.** It never existed for this
  model. Passing a mask through the image list is the supported path, not a workaround.
* **The model can draw a mask**, because a mask is just an image. That is what `/mask` is, and it is
  why the two-step "change only the hair" flow needs no segmentation model - no SAM, no detector, no
  second set of weights.

### 2.1 Which is why `/mask` normalises

What comes back from a mask request is a *picture of* a mask: anti-aliased edges, "white" around
250, sometimes a helpful text label. Everything downstream assumes `{0, 255}`, so `mask_ops.binarize`
cleans it up once, centrally, and both `/mask` and `/edit` run every mask through it - including one
a caller supplied, which may well have come from an editor or a JPEG.

The threshold is **Otsu's, not a fixed 128**. The model's idea of "black" drifts with the subject: a
mask over a bright region comes back lighter overall, and a fixed cut either swallows the region or
keeps the background.

### 2.2 🔴 `/mask` does not work well, and `EDIT` does not need it

**Verified against live weights on 2026-09-23, and this is the finding that matters most.**

The mechanism is sound: masks come back as clean 8-bit `{0, 255}` at the source resolution,
`binarize` does its job, provenance is stamped. What fails is the model's **semantic precision**.

| Asked for | Got |
|---|---|
| "the woman's hair" | a clean silhouette of her **entire head and shoulders** |
| "the black leather jacket" | a mostly-white image with a few black blobs - roughly **inverted** |

Qwen-Image-2.1 is a generative model being asked to do segmentation, and it does not do it. A
technically perfect mask of the wrong region is worse than no mask, because nothing downstream can
tell.

**And it is not needed for the case it was built for.** A plain `EDIT` with no mask -
*"change her hair colour to dark brown, almost black; keep everything else exactly the same"* -
produced exactly that: hair changed, identity, jacket, earring, pose and background all preserved.
The instruction-following is strong enough that the two-step flow buys nothing here.

So:

* **Use `EDIT` with a plain instruction.** That is the supported path and it works.
* **Treat `MASK` as experimental.** It is kept because the plumbing is correct and a future
  checkpoint may segment better, not because it is usable today.
* **If hard region control is genuinely needed**, get the mask from a real segmentation model.
  `sam2` (port 9130) is already in the tree and its output is an `artifact/image` that wires
  straight into this node's `mask` port - no new code required.

Example images and the full run are in `metaloom/scratchpad/qwen-image-2.1-examples/`.

### 2.3 `composite` is off by default

`composite: true` alpha-blends the result back over the original through the mask, guaranteeing that
nothing outside the region moved. It is **not** the default, because passing the mask as a condition
image is the model's own preservation mechanism and is usually enough - and because the pipeline
renders at `output_resolution` rather than at the source's size, so compositing means upscaling the
generated pixels back, which costs quality on the edited region too.

## 3. The contract

| Method | Path | Request | Response |
|---|---|---|---|
| `GET` | `/health` | - | JSON: status, model, device, capabilities, licence |
| `POST` | `/generate` | `{prompt, width, height, steps, seed?, negative_prompt?, true_cfg_scale?}` | `image/png` |
| `POST` | `/remix` | `{image_b64, prompt, strength, steps, seed?}` | `image/png` |
| `POST` | `/edit` | see below | `image/png` |
| `POST` | `/mask` | `{image_b64, prompt, steps, seed?, output_resolution?}` | `image/png`, 8-bit L, `{0,255}` |

`/generate` and `/remix` are byte-compatible with `ideogram-sidecar` and `mage-flow-sidecar`. That is
deliberate: it keeps the fleet's standing decision intact - there is no backend enum, the port is the
selector - so an existing pipeline moves here by changing one integer.

`strength` on `/remix` is accepted and **ignored**: Qwen-Image-2.1 is an instruction-edit model with
no denoise-strength knob, exactly as mage-flow is.

### `POST /edit`

```jsonc
{
  "prompt": "the person from image 1 holding the product from image 2",
  "images_b64": ["...", "..."],   // 1..10. [0] is the image being EDITED; the rest are references
  "mask_b64": null,               // a binary mask, white = the region that may change
  "mask_prompt": null,            // ...or name the region and let the sidecar derive the mask
  "width": null, "height": null,  // omitted -> derived from images_b64[0]'s aspect ratio
  "output_resolution": 1024,
  "steps": 40, "seed": null,
  "negative_prompt": null, "true_cfg_scale": 1.0,
  "composite": false
}
```

**The order of `images_b64` is significant.** Element 0 is edited; the rest are references. Nothing
in the response reveals a wrong order - it produces a plausible picture of the wrong thing.

`mask_prompt` runs **both passes in one request**: one lock acquisition, one resident model, no round
trip carrying a multi-megabyte PNG back and forth. It is mutually exclusive with `mask_b64` (400),
because they answer the same question and silently honouring one would leave the caller believing the
other took effect.

`true_cfg_scale` must be **above 1.0** for `negative_prompt` to do anything; at 1.0 the negative
branch is not evaluated at all. Both node and MCP client omit the pair entirely below that threshold,
so a sidecar log never shows a setting that did not take effect.

### Provenance

Every image response carries **`X-Model-Id`** and `qwenimage:*` PNG tEXt chunks (model, mode, prompt,
seed, steps). The raw-bytes contract leaves no JSON for it, and tEXt survives the file being written
to disk and picked up later. `ImageGenNode` reads the header and records it as the ledger row's
`producerVersion` - the first backend for which that column is not null.

## 4. Dimensions

`calculate_dimensions` in the pipeline rounds both sides to a **multiple of 32**; the VAE compresses
16x with the transformer consuming latents unpatched. The sidecar validates against
`[256, 2752]` - 2752 is the longest side in the model card's aspect-ratio table (16:9 at 2K) - and
**snaps** a non-multiple of 32 up while **rejecting** an out-of-range value. A caller asking for 4096
wants something this checkpoint cannot do, and quietly returning 2752 would hide that.

`width`/`height` are omitted entirely on `/edit` and `/remix`, which makes the pipeline derive the
size from the condition image's aspect ratio. That is what preserves an edit's framing and cannot be
expressed by picking a number.

Recommended 2K sizes from the model card: 1:1 2048x2048, 4:3 2400x1792, 3:4 1792x2400, 3:2
2528x1696, 2:3 1696x2528, 16:9 2752x1536, 9:16 1536x2752.

## 5. Environment variables

All `QWENIMAGE_`-prefixed, following `llamacpp` rather than the unprefixed `DEVICE` that `depth`,
`sentiment` and `tts` share. Read at **import time** into module constants; changing one needs a
process restart.

| Variable | Default | Meaning |
|---|---|---|
| `QWENIMAGE_MODEL` | `Qwen/Qwen-Image-2.1` | HF repo id or local path |
| `QWENIMAGE_DEVICE` | `cuda` if available | torch device |
| `QWENIMAGE_DTYPE` | `bfloat16` | the published dtype. `float16` gives NaN latents on long prompts |
| `QWENIMAGE_OFFLOAD` | `0` | `1` enables `enable_model_cpu_offload()` |
| `QWENIMAGE_STEPS` | `40` | the model card's default |
| `QWENIMAGE_OUTPUT_RESOLUTION` | `1024` | target side length; `2048` is native 2K at roughly 4x the cost |
| `QWENIMAGE_MAX_IMAGES` | `10` | cap on `images_b64` - the model's own limit |
| `QWENIMAGE_HOST` / `QWENIMAGE_PORT` | `0.0.0.0` / `9230` | read by **`server.py` as well as `run.sh`** |
| `CUDA_VISIBLE_DEVICES` | - | pin a card. 46 GB resident at 1K, 66 GB at 2K - see section 6.2 |

`QWENIMAGE_HOST`/`_PORT` being read in Python is a deliberate departure from the fleet: in `depth`,
`sentiment`, `tts`, `ltx2` and `mage-flow` those variables are read by `run.sh` only, so launching
`server.py` directly silently binds the hardcoded default.

## 6. Installation: diffusers comes from git

`QwenImage21Pipeline` was merged into diffusers on **2026-09-18** (PR #14804). The newest release,
**0.40.0**, shipped **2026-08-20** and cannot contain it, so `pip install diffusers` produces an
`ImportError` that reads like a typo.

`setup.sh` and the `Dockerfile` install it from git **pinned to the merge commit**
`6256aa7666cedd47443adc8f82da9a10e110b09c` rather than tracking `main`, so a rebuild months from now
still yields the pipeline this server was written against. The pin lives in **three places that must
agree**: `qwen_loader.DIFFUSERS_GIT_REF`, `setup.sh`, and the Dockerfile's `ARG DIFFUSERS_GIT_REF`.

`qwen_loader._require_pipeline()` turns the `ImportError` into a sentence naming the commit to
install, because the bare one reads as "diffusers is broken" and it is not.

`transformers>=5.17` is the model card's floor and resolves normally from PyPI - the text encoder is
a Qwen3-VL and needs `Qwen3VLProcessor` / `Qwen3VLForConditionalGeneration`.

### 6.2 torchvision is required, and nothing here imports it

🔴 **torch alone is not enough.** Loading the pipeline constructs `Qwen3VLProcessor`, which
constructs `Qwen3VLVideoProcessor`, which hard-requires **torchvision**. Without it the load fails
with:

```
ImportError: Qwen3VLVideoProcessor requires the Torchvision library but it was not found
```

This is easy to miss twice over: no file in this sidecar imports torchvision, and the sidecar never
touches video. The failure appears only on the first generation request, in a container that built
and started cleanly.

`setup.sh` and the `Dockerfile` therefore install `torch torchvision` on **one** line, from the same
index. Splitting them - torch from the CUDA index, torchvision from PyPI - is a subtler version of
the same bug, because the compiled ABIs then need not match.
`test_packaging.py::test_torch_and_torchvision_are_installed_together` pins both properties.

(Sections 6.1 and 6.2 were both written after the first live bring-up; see section 11.)

### 6.1 VRAM, measured

| Component | bf16 |
|---|---|
| text encoder (Qwen3-VL) | 17.5 GB |
| transformer (7B DiT) | 14.2 GB |
| VAE | 1.35 GB |
| **weights total** | **33 GB** |

The weights are not the number that matters. Measured on an H200 NVL (143 GB), idle between
requests:

| `output_resolution` | Resident VRAM | A 20-40 step generation |
|---|---|---|
| 1024 (default) | **46.3 GB** | 4 s at 8 steps, 8-14 s at 40 |
| 2048 (native 2K) | **65.5 GB** | 20 s at 20 steps |

The extra 13-33 GB over the weights is activations and the KV cache, and torch's caching allocator
**does not give it back** between requests - resident and peak are the same number, so a card sized
for the weights alone will OOM on the first generation.

**So: 48 GB is the practical floor for 1K and 80 GB for 2K.** An A100 80 GB or an H200 is
comfortable for both; a 40 GB A100 is not enough even at 1K. Below that, `QWENIMAGE_OFFLOAD=1` swaps
components CPU/GPU per stage at a real latency cost.

The first request after a cold start downloads and loads all of it - **minutes, not seconds**, and
easily mistaken for a hang. This is the fleet-wide lazy-load convention, not a quirk of this sidecar.

## 7. Licence: non-commercial

Qwen-Image-2.1 is released under the **Qwen RESEARCH LICENSE** (dated 2026-09-20), which grants use
"FOR NON-COMMERCIAL PURPOSES ONLY", defined as "for research or evaluation purposes only". Commercial
use requires a separate licence from Hangzhou Tongyi Laboratory
(`model-business@notice.qwencloud.com`).

This is **not** Apache-2.0. Qwen-Image **1.0** was; 2.1 is not, and the difference is easy to miss.

It places this backend alongside SDXL-Turbo and Ideogram-4 rather than alongside MIT-licensed
Mage-Flow, which **remains the documented default for shipping deployments**. The licence is recorded
in `website/content/english/docs/legal/model-licenses/` and stated in the sidecar's own `/health`
response, so an operator inspecting a running instance sees it without reading a spec.

Redistribution additionally requires carrying the agreement, marking modified files, and a "Built
with Qwen" notice on anything trained or fine-tuned from it.

## 8. Conventions and Gotchas

* **A mask is a condition image, not a parameter.** Section 2. This is the single thing to know.
* **`images_b64[0]` is the image being edited.** The rest are references. A wrong order is a
  plausible picture of the wrong thing and nothing in the response says so.
* **The mask polarity is a contract**: white marks what MAY change. Inverting it edits the
  background, which looks like a model failure rather than a caller error.
* **Look at the derived mask before trusting a masked edit.** `qwen_smoke.py edit --dump-mask` saves
  it. A wrong mask produces a completely plausible edit in entirely the wrong place - the one failure
  mode the output image will not reveal.
* **`--workers 1` is load-bearing.** The weights are a module global; a second worker would try to
  load its own 33 GB copy and OOM the card.
* **`_gpu_lock` serialises every pipeline call.** FastAPI dispatches sync handlers to a threadpool,
  so without it two concurrent requests would both allocate against a card already holding 33 GB.
* **A `mask_prompt` request runs two diffusion passes**, so it takes roughly twice as long as a plain
  edit. Both node and MCP timeouts are sized for that (120 s and 300 s respectively).
* **`strength` is inert**, as it is against mage-flow. The option is still accepted, so nothing warns
  you.
* **`negative_prompt` does nothing at `true_cfg_scale` 1.0** - the negative branch is not evaluated.
* **No auth, no TLS, binds `0.0.0.0`** - the fleet-wide position, and the fleet-wide problem.
* **`/health` is called by nobody.** No node polls it; a cold sidecar surfaces as a slow first
  request rather than a clear "not ready". `qwen_smoke.py health` is the human path.
* **`EDIT`/`MASK` against ports 9200 or 9210 fail with that sidecar's 404.** The node cannot check
  up front because it never calls `/health`.

## 10. Test Setup

The first Python tests in `sidecars/`. No GPU, no weights, no torch.

```bash
cd sidecars/qwen-image-sidecar
pip install pillow fastapi pydantic httpx2 pytest
python -m pytest test_mask_ops.py test_routes.py test_packaging.py -q
# or, with no pytest:
python test_mask_ops.py && python test_routes.py && python test_packaging.py
```

`test_routes.py` replaces the pipeline with a `FakePipe` that records its kwargs. What it pins is
**which images end up in the condition list, in what order, and what the prompt says about them** -
the assembly that is the entire design and is invisible from the outside. It says nothing about image
quality; that is a live-GPU question.

`test_packaging.py` parses the `Dockerfile` and asserts it copies every module `server.py` imports
(transitively), and that the diffusers pin agrees across `qwen_loader.py`, `setup.sh` and the
`Dockerfile`. It was written after the first deployment failed: `mask_ops.py` had been extracted for
testability and left out of the `COPY` line, so the image built and then died at import. The other
two suites cannot catch that class of bug, because they import from a working directory where every
file is present by definition.

Live bring-up against a deployed sidecar:

```bash
./qwen_smoke.py health   --endpoint http://HOST:9230
./qwen_smoke.py generate "a neon shop sign reading QWEN, rainy night"
./qwen_smoke.py compose a.png b.png c.png "the person from image 1 holding the product from image 2"
./qwen_smoke.py edit boy.jpg "dark brown hair" --mask-prompt "the boy's hair" --dump-mask
./qwen_smoke.py all sample.jpg          # every route; non-zero exit if any fails
```

Bodies go into a JSON payload rather than curl's argv deliberately: a base64-encoded image inlined
into argv blows the shell argument limit at around a 100 KB source image.
